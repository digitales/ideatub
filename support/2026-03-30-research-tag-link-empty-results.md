# Research Tag Link Shows Empty Results - Customer Support Investigation

**Date**: 2026-03-30
**Status**: Investigating
**Customer**: Internal support report
**Priority**: Medium
**Reported By**: Internal

## Issue Description
An imported research thought displays the tag `#research:newsletter-imported-625`, but clicking that tag opens the Stream view with `tag=research_newsletter_imported_625` and shows an empty state: `No thoughts with tag 'research_newsletter_imported_625'`.

## Customer Impact
- Affected users cannot navigate from imported research tags to the related document/thread in Stream.
- The issue breaks a primary discovery path for imported research content.
- This is likely to affect any tag containing punctuation that the frontend and backend normalize differently.

## Investigation Steps
1. Reviewed the Stream tag link rendering in `resources/views/idea/partials/thought_tag_row.blade.php`.
2. Confirmed the frontend slugging logic in `resources/js/app.js`.
3. Traced Stream tag resolution and filtering in `app/Http/Controllers/IdeaController.php`.
4. Traced research/import tag creation in `app/Services/ThoughtCaptureService.php` and the newsletter research flow.
5. Verified Laravel runtime behavior with `Str::slug('research:newsletter-imported-625', '_')`, which returns `researchnewsletter_imported_625`.
6. Checked existing Stream feature coverage and confirmed there is a URL-safe tag test for spaces, but no regression test for colon-delimited document tags.

## Root Cause Analysis
The imported research tag is stored canonically as `research:newsletter-imported-625`.

The clickable tag pill uses frontend slugging logic that replaces any non-alphanumeric run with `_`, producing `research_newsletter_imported_625`.

The Stream page resolves the incoming `tag` query parameter back to a canonical stored tag using Laravel `Str::slug($tag, '_')`. For colon-delimited tags, Laravel removes the colon instead of converting it to `_`, producing `researchnewsletter_imported_625`.

Because the frontend slug (`research_newsletter_imported_625`) does not match the backend slug (`researchnewsletter_imported_625`), `resolveTagSlugToCanonical()` returns `null`. The Stream query then intentionally applies `whereRaw('0 = 1')`, which guarantees an empty result set.

## Resolution
No application change was applied during this investigation.

Recommended fix:
- Use one shared normalization rule for tag URLs on both client and server.
- Prefer aligning the server-side resolver with the frontend slugging behavior, or generate tag URLs from the server.
- Add a regression test covering colon-delimited tags such as `research:newsletter-imported-625`.

## Customer Communication
- 2026-03-30: Root cause identified as a frontend/backend tag slug mismatch for colon-delimited tags. No data loss found; issue is in tag URL resolution.

## Prevention & Follow-up
- [ ] Update tag slug generation/resolution so both sides normalize punctuation identically.
- [ ] Add a feature test for Stream filtering using colon-delimited document tags.
- [ ] Audit other generated tags that include punctuation to confirm whether they are vulnerable to the same mismatch.

## Related Issues
- Potentially affects any `doc_type:slug` tag generated by `ThoughtCaptureService`.

## Lessons Learned
Document tags are stored canonically with `:` separators, but the app currently relies on two different slugification implementations when converting between display tags and Stream query params. This creates a hidden compatibility bug that does not appear for simple space-delimited tags.
